# 1. Product

## 1.1 Summary

Argus is a local web console that reads labeled network-flow benchmark data, aggregates observable flow information into fixed time windows, and produces a **risk score for whether the next time window contains malicious activity**.

The console shows:

- one-window-ahead risk over time,
- validation-selected alert thresholds,
- ground-truth attack periods for evaluation,
- honest comparison against baselines,
- local SHAP explanations for selected Random Forest alerts,
- optional retrospective ATT&CK context derived from dataset labels,
- optional analyst notes generated by a local Gemma model through Ollama,
- deterministic fallback notes if Ollama is unavailable.

**One-line pitch:**  
> A one-window-ahead network risk timeline that is evaluated chronologically, compared against strong baselines, and explains selected warnings.

## 1.2 Primary user

A SOC analyst, security researcher, or small IT/security team reviewing network-flow telemetry.

## 1.3 Problem

Flow-based security systems often present events one record at a time. Argus tests whether recent temporal patterns in aggregated traffic provide useful warning of malicious activity in the **next** time window and presents the result in a form an analyst can inspect.

## 1.4 Claims policy

The UI, README, About page, and demo must follow these rules:

- Say **“risk score”**, not “probability,” unless a future version explicitly calibrates probabilities.
- Say **“one-window-ahead early-warning experiment”** or **“next-window risk scoring.”**
- Do not call it a “world model,” “attack forecasting engine,” “production IDS,” or “production-ready SOC system.”
- “Early warning” means the model predicts the first malicious window from the preceding window. It does **not** mean long-horizon forecasting.
- Report **attack-onset recall** separately from overall recall.
- Always show the **oracle persistence diagnostic** and clearly label it as non-deployable because it uses dataset ground truth for the current window.
- Always show a deployable **current-window logistic-regression baseline**.
- ATT&CK/stage context is a **retrospective lookup from dataset labels**, not a prediction.
- Gemma never affects the risk score.
- Ground-truth labels, attack categories, and evaluation stage must never be presented as information that would be available to a live analyst before the event occurs.
- Public benchmark captures are not live production traffic.
- Dataset age, synthetic traffic, capture methodology, uncertain labels, and other selected-dataset limitations must be stated on the About page.
- If the main model does not beat a baseline, show that result honestly.

# 4. Temporal semantics and leakage policy

This section is non-negotiable.

## 4.1 Normalized flow contract

`ml/adapters/<dataset>.py` returns a DataFrame with these normalized fields:

Required:

- `start_ts` — float seconds
- `available_ts` — float seconds; earliest time the full feature values used by Argus are observable
- `src_ip`
- `dst_ip`
- `src_port`
- `dst_port`
- `proto`
- `dur`
- `bytes`
- `packets`
- `label` — 0 or 1
- `sequence_id`

Optional:

- `end_ts`
- `state`
- `attack_cat`

Rules:

- If final flow bytes/packets/duration/state are used, `available_ts` must normally reflect flow completion/end/record availability, not flow start.
- If the dataset cannot support an honest `available_ts` for the chosen feature set, either:
  1. remove those future-dependent features, or
  2. reject the dataset for the primary experiment.
- Optional missing columns are represented explicitly with `NaN`/`null`.
- No label field may enter model features.

## 4.2 Window timeline

Config:

```yaml
window_seconds: 10
lookback_windows: 5
min_malicious_flows: 1
max_gap_windows: 60
random_seed: 42
default_model: rf
```

Rules:

- Fixed, non-overlapping windows.
- Window boundaries are aligned independently within each `sequence_id`.
- Ground-truth malicious activity for a window is based on flow **occurrence/start time** unless S0 documents a dataset-specific reason otherwise.
- Feature aggregation for window `t` uses only flow information with `available_ts` inside or before the end of window `t`.
- No sample may use information that becomes available after its prediction cutoff.
- Zero-observation windows may be represented as zero-count windows.
- After more than `max_gap_windows` consecutive missing/idle windows, start a new logical sequence.
- Never create lag features across a sequence reset or capture boundary.

## 4.3 Per-window features

Only features observable by the cutoff may be used.

Core features:

- flow count,
- total bytes,
- total packets,
- unique source IPs,
- unique destination IPs,
- unique destination ports,
- per-protocol fractions,
- port-diversity ratio,
- destination-port entropy,
- mean/std/max duration,
- mean/std/max bytes per flow,
- state failure/reset ratio if a defensible state field exists.

Feature availability must be explicit. If a feature cannot be computed for the selected dataset, omit it and record that omission.

## 4.4 Lag design

At prediction time for window `t+1`, input may use:

- current feature vector at `t`,
- feature vectors `t-L+1 ... t`,
- first differences of selected count features.

No future window contributes to the input.

## 4.5 Target

For sample ending at window `t`:

```text
truth_next = 1
if window t+1 contains at least min_malicious_flows malicious flows
else 0
```

Default:

```text
min_malicious_flows = 1
```

The target rule is fixed before final test evaluation.

## 4.6 Split

Chronological only.

Default:

- 70% train
- 10% validation
- 20% test

Rules:

- Split assignment is based on the **target window timestamp**.
- No random shuffling.
- Scalers/imputers fit on train only.
- Hyperparameters, feature decisions, thresholds, W/L choices, and target-rule changes use train/validation only.
- Final test is evaluated only after configuration is frozen.
- Do not cross `sequence_id` boundaries.
- If the selected dataset consists of independent captures that cannot be ordered meaningfully, Sol must document a defensible alternative or reject it as primary.

## 4.7 Leakage tests

Required tests:

1. Alter/remove any flow whose `available_ts` is after cutoff `t`; features at `t` must not change.
2. Include a flow starting before `t` but finishing after `t`; final-flow values must not appear before `available_ts`.
3. Train target timestamps precede validation targets; validation targets precede test targets for any continuous sequence.
4. `label`, `attack_cat`, `truth_now`, `truth_next`, and any derivative of them are absent from model feature columns.
5. `truth_now` is used only by the oracle persistence diagnostic.
6. No lag sample crosses `sequence_id` or gap-reset boundaries.

# 5. Models and evaluation

## 5.1 Models

### A. `oracle_persistence`
Diagnostic only.

```text
risk_score = truth_now
prediction = truth_now
```

This is **not deployable** because it uses current-window dataset ground truth.

Purpose:
- measure how strong temporal attack persistence is,
- expose whether the task is trivially dominated by attack continuation.

### B. `lr_current`
Deployable baseline.

Input:
- only features from current window `t`.

Target:
- `truth_next`.

Use:
- logistic regression,
- train-only preprocessing,
- class weighting derived from training data.

### C. `lr_lag`
Lagged linear model.

Input:
- same lagged feature representation used for Random Forest.

Use:
- logistic regression,
- class weighting derived from training data.

### D. `rf`
Default main model.

Use:
- Random Forest,
- imbalance handling derived from training data only,
- fixed random seed.

Do not substitute gradient boosting during the hackathon unless Astra explicitly changes the contract.

## 5.2 Risk score terminology

Model outputs are called **risk scores**.

Do not claim they are calibrated event probabilities.

## 5.3 Threshold selection

For each predictive model (`lr_current`, `lr_lag`, `rf`):

- choose its threshold on validation only,
- default policy: maximize validation F1,
- freeze threshold before test,
- store the threshold separately for each model.

`oracle_persistence` has no learned threshold.

## 5.4 Required metrics

For each model:

- precision,
- recall,
- F1,
- false-positive rate,
- PR-AUC where a continuous score exists,
- confusion matrix,
- median inference latency per window,
- attack-onset recall.

Attack onset:

```text
onset window = truth_now == 0 and truth_next == 1
```

Also report:

- `test_windows`
- `positive_rate`
- `attack_onset_windows`
- `continuation_windows`

The demo must not use overall recall as evidence of “early warning” without also showing onset recall.

## 5.5 Test policy

`ml/evaluate.py`:

- loads a frozen run config,
- evaluates test once,
- writes deterministic artifacts,
- stores seed and hyperparameters,
- produces the same numbers on repeated runs from the same processed data.

# 6. Explainability and retrospective attack context

## 6.1 SHAP

SHAP is for the Random Forest only.

Use `TreeExplainer` if compatible with the installed environment.

Generate local explanations for:

- highest-risk flagged test windows up to a configured cap,
- at least one unflagged sample if time allows.

Recommended cap:

```yaml
max_explained_test_windows: 200
```

For each explained window:

- return up to 5 features,
- sort by absolute SHAP magnitude,
- include feature value and signed SHAP value.

If SHAP fails:

- set `explanation_available: false`,
- set `top_features: []`,
- add a caveat to `metrics.json`,
- show a proper UI empty state.

**Do not substitute global feature importance or permutation importance and present it as a per-window explanation.**

## 6.2 ATT&CK / stage context

This is optional retrospective evaluation context.

Rules:

- Derived only from dataset labels/categories.
- Never fed into the ML model.
- Never fed into Gemma analyst-note generation.
- Never described as a prediction.
- Ambiguous categories map to `null`.
- Mapping is manually reviewed before the demo.
- If the selected dataset lacks a defensible category mapping, disable this feature.

UI wording:

> Retrospective dataset-label context. Not predicted and not available to the model.

## 10.1 Client

Endpoint:

```text
http://localhost:11434/api/generate
```

Request behavior:

```json
{
  "stream": false,
  "format": "json",
  "options": {
    "temperature": 0
  }
}
```

Model:

```text
OLLAMA_MODEL
```

Default:

```text
gemma4:e2b-mlx
```

Astra must run `ollama list` during preflight.

Local presence of the tag is not assumed.

## 10.2 Prompt inputs

Gemma may receive only operational model output:

- risk score,
- flagged status,
- top SHAP features and values,
- window counts.

Do **not** send:

- `truth_now`,
- `truth_next`,
- dataset attack category,
- evaluation stage,
- future-window information.

## 10.3 Fallback

Fallback triggers on:

- connection error,
- timeout,
- invalid JSON,
- missing model,
- Ollama unavailable.

Default timeout:

```text
20 seconds
```

Pre-warm Ollama before the demo if available.

The demo must remain fully usable without Ollama.

## 10.4 Cache

Luna writes note cache to:

```text
runtime/notes_cache.json
```

Not `artifacts/`.

`runtime/` is gitignored and owned by Luna.

# 16. Judge-facing interpretation rules

The demo must distinguish three things:

## 16.1 What the model knows

At cutoff `t`, the model may know only:

- observable aggregated traffic through `t`,
- lagged observable traffic through `t`.

## 16.2 What evaluation knows

Evaluation may know:

- `truth_now`,
- `truth_next`,
- attack category,
- retrospective stage.

These fields must be visually identified as evaluation-only.

## 16.3 What Gemma knows

Gemma may know only:

- the model risk score,
- alert state,
- model explanation,
- aggregate counts.

Gemma may not receive ground truth.
